# Poker Night — спецификация

Версия документа: 1.0 · дата: 2026-10-29 · статус: готово к реализации

Мобильное SPA для домашних покерных вечеров: раздача фишек из набора, учёт докупок и выводов
игроков, итоги вечера и публичная ссылка на результаты. Бэкенда нет, всё живёт в браузере.

---

## 1. Область и цели

### 1.1 Что делает приложение

1. Пользователь настраивает **свой набор фишек** (номиналы, цвета, количество).
2. Создаёт **игру (сессию)**: состав игроков, стек в монетах, курс «фишек за монету», малый блайнд,
   кратность K, резерв на докупки.
3. Приложение **считает раздачу**: сколько фишек каждого номинала выдать каждому игроку, чтобы
   набрать ровно стек и оставить запас в наборе на докупки. Предлагается 3 варианта.
4. Во время игры пользователь отмечает **докупки**, **выходы игроков** с остатком и **внешние покупки**
   (стек переходит от игрока к игроку за реальные деньги).
5. В конце — **экран итогов** (фишки и монеты: кто выиграл/проиграл), **архивация** с подтверждением
   мини-игрой и **публичная ссылка** с зашитыми в URL итогами.
6. **История** всех сессий, возможность начать новую игру с теми же настройками.

### 1.2 Не цели

- Не покерный движок: карты, ставки, банк розыгрыша не моделируются.
- Нет мультиплеера, аккаунтов, синхронизации между устройствами.
- Нет бэкенда, аналитики, телеметрии.
- Нет мультиязычности (только русский), только тёмная тема.
- Мультивкладочность не поддерживается (см. §12.6).

### 1.3 Термины

| Термин | Значение |
|---|---|
| **Фишка** | Физический жетон. Номинал — целое число на жетоне (5, 25, 50, 100). |
| **Монета** | Условная денежная единица вечера. 1 монета = `rate` фишек. |
| **Курс (`rate`)** | Целое число фишек за 1 монету. Дефолт 4. В UI подписан «фишек за монету». |
| **Стек** | Стартовый набор игрока, задаётся **в монетах**. В фишках = `stackCoins × rate`. |
| **Набор** | Инвентарь фишек пользователя: список `{номинал, цвет, количество}`. |
| **Игра / сессия** | Один вечер: настройки + журнал событий + итоги. |
| **Докупка** | Игрок получает ещё один стандартный стек фишек. |
| **Внешняя покупка** | Стек переходит от одного игрока к другому за деньги вне банка. |
| **K** | Кратность: количество фишек каждого номинала в раздаче кратно K. |
| **Резерв** | Сколько полных стеков банк должен оставить на докупки. |

## 3. Модель данных

### 3.1 Числа

- **Фишки** — всегда целые (`number`, integer).
- **Монеты** — хранятся как **целые сотые монеты** (`cents`), чтобы не ловить float-ошибки.
  `1 монета = 100`. Ввод пользователя в монетах конвертируется один раз при сохранении.
- Формат вывода: `ru-RU`, монеты — до 2 знаков, но `.00` отбрасывается (`310`, `77.5`, `77.25`).

```ts
type Chips = number;      // целое
type CoinCents = number;  // целое, 1 монета = 100
```

### 3.2 Типы

```ts
// ---------- Набор ----------
interface Denomination {
  id: string;          // crypto.randomUUID() — встроен, зависимостей не нужно
  value: Chips;        // номинал, > 0, целое
  color: string;       // hex из палитры (#RRGGBB)
  count: number;       // количество в наборе, >= 0
}

interface Kit {
  id: 'kit';           // singleton
  denominations: Denomination[];   // 2..8, строго возрастают по value
  updatedAt: string;               // ISO 8601
}

// ---------- Дефолты новой игры ----------
interface Defaults {
  id: 'defaults';
  stackCoins: number;    // стек в монетах, целое > 0
  rate: number;          // фишек за монету, целое >= 1
  smallBlindChips: Chips;
  multipleK: 4 | 5 | 10;
  reserveStacks: number; // сколько полных стеков держать в резерве, >= 0
  updatedAt: string;
}

// ---------- Игра ----------
type GameStatus = 'active' | 'finished' | 'archived';

interface Player {
  id: string;
  name: string;         // 1..24 символа, уникален в игре
  seat: number;         // порядок в списке
}

// Производные величины — только в памяти, не в базе
interface PlayerState extends Player {
  chips: Chips;         // фишки на руках (из журнала)
  buyins: number;       // докупок из банка
  externalIn: number;   // внешних стеков получено
  externalOut: number;  // внешних стеков отдано
  out: boolean;         // вышел из игры
  finalChips?: Chips;   // undefined = остаток не зафиксирован
  netChips: Chips;
}
```

**Производные величины игрока НЕ хранятся в базе.** `chips`, `buyins`, `externalIn`,
`externalOut`, `out`, `finalChips`, `netChips` вычисляются из журнала функцией
`derivePlayers(game)` (§3.4). В IndexedDB пишется только `Game` с `players: Player[]`
(id, имя, место) и `events: GameEvent[]`. Причина: журнал — единственный источник правды,
а дублирование производных величин рано или поздно рассинхронизируется.

```ts
interface Game {
  id: string;
  name: string;              // автоимя «29 окт 20:45» или введённое
  createdAt: string;         // ISO 8601 с offset
  status: GameStatus;

  // замороженная копия настроек (архивы стабильны)
  rate: number;
  stackCoins: number;
  stackChips: Chips;         // stackCoins * rate
  smallBlindChips: Chips;
  multipleK: 4 | 5 | 10;
  reserveStacks: number;
  denominations: Denomination[];   // копия набора на момент старта

  players: Player[];
  deal: Deal;                // выбранный вариант раздачи
  events: GameEvent[];       // журнал, хронологический порядок
  archivedAt?: string;
  schemaVersion: 1;
}

interface Deal {
  variant: 'balanced' | 'economy' | 'speed';
  perPlayer: { value: Chips; count: number }[];  // одинаково для всех
  chipsPerPlayer: Chips;     // сумма perPlayer
  totalDealt: Chips;         // chipsPerPlayer * players.length
  level: DealLevel;          // какой уровень компромисса сработал
  exemptValue?: Chips;       // номинал, освобождённый от K
}

type DealLevel = 'L0' | 'L1' | 'L2' | 'L3' | 'L4';
```

### 3.3 Журнал событий

События — единственный источник правды о том, что произошло. Все производные величины
(фишки на руках, остаток банка, итоги) **вычисляются** из журнала, а не хранятся.

```ts
type GameEvent =
  | { id: string; t: string; type: 'deal';        playerId: string; chips: Chips }
  | { id: string; t: string; type: 'buyin';       playerId: string; chips: Chips }
  | { id: string; t: string; type: 'external';    fromId: string; toId: string; chips: Chips }
  | { id: string; t: string; type: 'cashout';     playerId: string; chips: Chips }
  | { id: string; t: string; type: 'finalStack';  playerId: string; chips: Chips };
```

- `t` — ISO 8601 с локальным offset.
- `deal` создаётся автоматически при старте игры, по одному на игрока.
- `cashout` = игрок вышел, указан остаток. **Возврата нет** (см. §6.4).
- `finalStack` = финальный остаток на экране итогов. Может существовать вместе с `cashout`
  (тогда `cashout` — это выход раньше, а `finalStack` — остаток на момент конца).

### 3.4 Правила вычисления (чистые функции в `core/totals.ts`)

```
// 1. Фишки, физически лежащие перед игроком прямо сейчас
chipsOnHand(p) = Σ chips(deal, p) + Σ chips(buyin, p)
               + Σ chips(external, toId = p) − Σ chips(external, fromId = p)
               − Σ chips(cashout, p)

// 2. Чем игрок «закрывается» в итогах
finalChips(p) =
    chips(finalStack, p)          если есть событие finalStack (перезапись, не сумма)
  = chips(последний cashout, p)   если игрок вышел и finalStack не задан
  = chipsOnHand(p)                иначе             ← помечается «остаток не зафиксирован»,
                                                    если игрок не выходил и не фиксировал

// 3. Сколько фишек игрок оплатил — ВСЕГДА включая стартовый стек
boughtChips(p)     = stackChips × (1 + buyins(p) + externalIn(p))
externalOutChips(p)= stackChips × externalOut(p)

// 4. Итог
netChips(p) = finalChips(p) + externalOutChips(p) − boughtChips(p)
netCoins(p) = netChips(p) / rate           // для UI, округление до 2 знаков

// 5. Банк (только физические фишки набора; внешние покупки его не двигают)
bankRemaining = kitTotalChips
              − Σ chips(deal)
              − Σ chips(buyin)
              + Σ chips(cashout)
```

### 3.4.1 Единственная тонкость: `chips` у события `finalStack` — абсолютный остаток

`finalStack` **не накапливается**: если игрок дважды ввёл остаток, применяется последнее
событие, а не сумма. То же для `cashout` (повторный выход перезаписывает предыдущий).

Это отражено в `derivePlayers`: см. `finalChips(p)` выше.

### 3.4.2 Сводка по всем событиям

```ts
interface PlayerTotals {
  playerId: string;
  name: string;
  chipsOnHand: Chips;      // физически на руках
  finalChips: Chips | null;// null = остаток не зафиксирован
  boughtChips: Chips;      // оплачено всего (включая стартовый стек)
  externalOutChips: Chips; // продано другим игрокам
  netChips: Chips;
  netCoins: number;        // для UI
}

interface GameTotals {
  players: PlayerTotals[];
  sumNetChips: Chips;      // должно быть 0
  reconciled: boolean;
  bankRemainingChips: Chips;
  bankRemainingCoins: number;
  uncoveredCount: number;  // сколько игроков без финального остатка
}
```

**Почему `boughtChips` включает стартовый стек.** Игрок «должен банку» за всё, что
получил: стартовый стек, докупки и внешние покупки. Продажа стека другому игроку
компенсируется через `externalOutChips`. Проверка на примере (стек 2000, 2 игрока):

- A продаёт свой стартовый стек B за деньги: `final = cashout 0`, `externalOut = 2000`,
  `bought = 2000` → `net = 0 + 2000 − 2000 = 0` ✔ (A вернул свои деньги, ничего не выиграл).
- B купил: `final = 4000`, `externalIn = 2000`, `bought = 2000 × (1 + 0 + 1) = 4000`
  → `net = 4000 − 4000 = 0` ✔.
- Сумма = 0 ✔.

**Почему `cashout` входит в `finalChips`.** Вышедший игрок вернул фишки в банк, поэтому
`chipsOnHand` у него 0; но его итог — это остаток на момент выхода, а не ноль.

Проверка сходимости (Q14): `Σ netChips(p) == 0` при корректном журнале и заполненных
`finalStack`/`cashout`. Допустимое расхождение — 0. Если не сходится, показывается плашка
«не сходится на N фишек»; архивация **не блокируется**.

### 3.5 Проверенные примеры расчёта (golden fixtures для `totals.test.ts`)

Набор 12 250 фишек, стек 600 (150 монет × курс 4).

**Пример A — обычная игра, 4 игрока, одна докупка.**

События: `deal×4` по 600, `buyin(a)` 600, `cashout`: a=1500, b=300, c=500, d=100.

| Игрок | on hand | final | bought | net фишек | net монет |
|---|---|---|---|---|---|
| a | 0 | 1500 | 1200 | **+300** | +75 |
| b | 0 | 300 | 600 | **−300** | −75 |
| c | 0 | 500 | 600 | **−100** | −25 |
| d | 0 | 100 | 600 | **−500** | −125 |

`Σ net = −600`, банк = 11 650. Расхождение −600 означает: 600 фишек остались
на столе и не были зафиксированы. Плашка «не сходится на 600 фишек». Это **корректно
обнаруженная** ошибка ввода, а не баг: сумма `cashout` (2 400) меньше выданного (3 000).

**Пример B — внешняя покупка, 2 игрока.**

События: `deal(a)=600`, `deal(b)=600`, `external(from a, to b)=600`,
`cashout(a)=0`, `cashout(b)=1200`.

| Игрок | final | externalOut | bought | net |
|---|---|---|---|---|
| a | 0 | 600 | 600 | **0** |
| b | 1200 | 0 | 1200 | **0** |

`Σ net = 0` ✔. Банк = 12 250 (не изменился) ✔. A продал свой стек за деньги и вышел
в ноль; B заплатил A и остался в ноль. Оба «при своих» — ровно то, что произошло.

**Пример C — внешняя покупка + докупка из банка.**

События: `deal(a)=600`, `deal(b)=600`, `external(a→b)=600`, `buyin(a)=600`,
`cashout(a)=700`, `cashout(b)=1100`.

| Игрок | final | externalOut | bought | net |
|---|---|---|---|---|
| a | 700 | 600 | 1200 | **+100** |
| b | 1100 | 0 | 1200 | **−100** |

`Σ net = 0` ✔. Банк = 12 250 ✔ (600 ушло на `buyin`, 600+1100 вернулось).

Эти три примера обязательны в `src/core/totals.test.ts`.

## 4. Алгоритм раздачи

### 4.1 Постановка

Дано:
- `denoms` — номиналы набора, возрастающие: `d[0] < d[1] < … < d[m-1]`;
- `counts[i]` — количество фишек номинала `i` в наборе;
- `n` — число игроков (2..12);
- `stackChips` — целевая сумма на игрока;
- `K` — кратность (4, 5 или 10);
- `variant` — `balanced | economy | speed`.

Нужно найти вектор `a[0..m-1]` (количество фишек каждого номинала **одному игроку**),
одинаковый для всех игроков, такой что:

1. `Σ a[i]·d[i] = target` — точная сумма (с оговорками уровней, §4.4);
2. `a[i] ≤ floor(counts[i] / n)` — набора хватает на всех;
3. `a[i] ≡ 0 (mod K)` — для всех `i`, **кроме одного** исключённого номинала `exempt`;
4. `a[0] ≥ 4` — минимум 4 фишки младшего номинала (блайнды);
   `a[1] ≥ 2`, если `a[1] > 0` — минимум 2 фишки следующего номинала.

Ограничение (3) с единственным исключением — не «добивка ≤ 2 мелких», а именно **освобождение
одного номинала от кратности**. Обоснование: алгебраически при K, не делящем целевой стек,
иначе точная сумма недостижима (проверено перебором, §4.7).

Целевая функция — лексикографическая, зависит от варианта (`§4.3`).

### 4.2 Почему задача решается перебором

`m ≤ 8`, `n ≤ 12`, а количество фишек одного номинала на игрока ограничено
`floor(counts[i]/n)` — обычно ≤ 37. Пространство поиска с учётом отсечения по остатку
(`rem > suffix[i] → отсечь`) составляет **менее 500 узлов** на конфигурацию. Замеры: 0.0–0.4 мс
на ноутбуке; на телефоне с запасом < 20 мс. Динамическое программирование не нужно,
перебор даёт точный оптимум и позволяет легко менять целевую функцию.

### 4.3 Целевые функции вариантов

| Вариант | Что оптимизируем | Лексикографический критерий |
|---|---|---|
| **Balanced** | Нечем разменивать не должно быть | `min (провалы в верху стека)`, затем `min (перекос верха, в фишках)`, затем `min (кол-во ненулевых номиналов)`, затем `min (общее число фишек)` |
| **Economy** | Максимум остатка в банке | `min (общее число фишек)`, затем `min (кол-во ненулевых)` |
| **Speed** | Больше мелких для выплат | `max (a[0])`, затем `min (общее число фишек)` |

Все три дают **ровно стек** и **одинаковый набор всем игрокам** (Q18, Q54).

**Почему Balanced не «минимум номиналов».** Чистый `min (ненулевых)` выбирал
первое попавшееся решение с минимумом номиналов, и стек получался с дырами:
`5,25,50,100` давали ноль по **50** при пяти **100** (`[10,0,5,17]`), ноль по
**25** при живых 50 и 100 (`[8,8,5,8]`) — старшую фишку нечем разменять.

Определения (номиналы отсортированы по возрастанию, `top` — самый крупный из
выданных):

- «верх» — выданные номиналы весом `≥ top/10`. Для `5,25,50,100` это `25,50,100`,
  а `5` — мелкий размен.
- «провал»=`gaps` — пропущенный номинал верха, за которым снова что-то выдано:
  `[15,11,5,0]` → 0, `[10,18,10,10]` → 0, `[10,0,5,17]` → 1 (пропущен 25),
  `[8,8,0,8]` → 1 (пропущен 50),
  `[10,10,0,5]` → 1 (пропущен 50), `[5,3,0,5]` → 0 (пробел только в хвосте —
  разменять нечего, но и жертвовать нечем).
- «перекос верха»=`coarseSpread` — в фишках: `max(a[i]·d[i]) − min(a[i]·d[i])`
  по выданным номиналам верха.

`gaps` важен больше экономии номиналов: сначала заполняем верх, потом режем
число номиналов. `coarseSpread` даёт вместо «5×100 и 0×50» примерно поровну
(`[10,18,10,10]` = 100+450+500+100) или сдвиг к мелким, если верх не сходится.

Дыры, которые остаются и после этого, — не баг критерия, а следствие §4.1
(правил блайндов и кратности K), они перечислены в §4.7.

### 4.3.1 Как Balanced держится на псевдокоде §4.5

`score(s, variant, denoms)` возвращает массив чисел; сравнение — лексикографическое.
Для `balanced`: `[gaps, coarseSpread, nonZero, total]`. Чтобы посчитать `gaps` и
`coarseSpread`, в `score` и `better` пробрасывается `denoms` (номиналы), а не
только вектор `counts`.

### 4.4 Лестница компромиссов (ladder)

Алгоритм пытается решить задачу на уровнях, от самого строгого к самому мягкому.
Первый успешный уровень фиксируется в `deal.level` и **показывается пользователю**.

```
maxReachable = максимум достижимой суммы при ограничениях по количеству (без K)
T            = min(stackChips, maxReachable)

L0  точная сумма T, K включён, блайнды строго (a[0] ≥ 4; a[1] ∈ {0} ∪ [2, ∞))
L1  точная сумма T, K включён, блайнды не проверяются
L2  сумма T−1, затем T−2, K включён, блайнды не проверяются
L3  точная сумма T, K ВЫКЛЮЧЕН
L4  максимальная достижимая сумма ≤ T, K выключен (перебор вниз от maxReachable)
```

- `L0` → «ровно стек, кратность соблюдена, мелкие на блайнды гарантированы».
- `L1` → «ровно стек, кратность соблюдена, но мелких на блайнды может не хватить».
- `L2` → «стек отличается на 1–2 фишки» (показывается явно).
- `L3` → «кратность K ослаблена» (показывается явно).
- `L4` → «банк не позволяет выдать полный стек» (показывается явно + размер недобора).

Если `stackChips > maxReachable`, целевой стек симметрично урезается до `maxReachable`
и в UI показывается покрытие докупок (Q4, Q142).

### 4.5 Псевдокод

```ts
type Variant = 'balanced' | 'economy' | 'speed';

interface DealInput {
  denominations: { value: Chips; count: number }[];
  players: number;
  targetChips: Chips;
  K: 4 | 5 | 10;
  variant: Variant;
}

interface DealResult {
  perPlayer: { value: Chips; count: number }[];
  chipsPerPlayer: Chips;
  level: 'L0' | 'L1' | 'L2' | 'L3' | 'L4';
  exemptValue?: Chips;
  note?: string;   // человекочитаемое пояснение для UI
}

function solveDeal(input: DealInput): DealResult | null {
  const { denominations, players, targetChips, K, variant } = input;
  const d = denominations.map(x => x.value);
  const cap = denominations.map(x => Math.floor(x.count / players));

  // суффиксные суммы для отсечения
  const suffix: number[] = [];
  for (let i = d.length; i >= 0; i--) suffix[i] = (suffix[i + 1] ?? 0) + (i < d.length ? cap[i] * d[i] : 0);

  const t = Math.min(targetChips, suffix[0]);

  // --- ядро перебора ---
  // counts: текущий вектор; best: лучший найденный
  function search(target: Chips, useK: boolean, strictBlinds: boolean): Solution | null {
    // ВАЖНО: перебираем ВСЕ варианты exempt и оставляем лучший по целевой функции.
    // Нельзя останавливаться на первом успешном: разные exempt дают разные векторы,
    // и «первый» — не «оптимальный».
    let best: Solution | null = null;
    for (const exempt of useK ? [-1, ...d.keys()] : [-1]) {
      const found = dfs(0, target, exempt);
      if (found && better(found, best, variant)) best = found;
    }
    return best;
  }

  function dfs(i: number, rem: Chips, exempt: number): Solution | null {
    if (i === d.length) return rem === 0 ? snapshot() : null;
    if (rem > suffix[i]) return null;                 // отсечение: нечем добрать

    let best: Solution | null = null;
    const max = Math.min(cap[i], Math.floor(rem / d[i]));

    for (let a = 0; a <= max; a++) {
      if (useK && i !== exempt && a % K !== 0) continue;
      if (strictBlinds && i === 0 && a < 4) continue;
      if (strictBlinds && i === 1 && a > 0 && a < 2) continue;

      const v = a * d[i];
      if (rem - v > suffix[i + 1]) continue;          // отсечение

      counts[i] = a;
      const cand = dfs(i + 1, rem - v, exempt);
      if (cand && better(cand, best, variant)) best = cand;
    }
    counts[i] = 0;
    return best;
  }

  // --- лестница ---
  let sol = search(t, true, true);
  if (sol) return finish(sol, 'L0');

  sol = search(t, true, false);
  if (sol) return finish(sol, 'L1');

  for (const dev of [1, 2]) {
    if (t - dev <= 0) continue;
    sol = search(t - dev, true, false);
    if (sol) return finish(sol, 'L2', `−${dev} фишки на игрока`);
  }

  sol = search(t, false, false);
  if (sol) return finish(sol, 'L3', 'кратность ослаблена');

  // L4: стартуем с максимально достижимой суммы, а не с t —
  // иначе на больших стеках цикл вниз делает лишнюю работу.
  const reachable = maxReachable(d, cap);          // bounded knapsack, см. ниже
  for (let target = Math.min(t, reachable); target > 0; target--) {
    sol = search(target, false, false);
    if (sol) return finish(sol, 'L4', `доступно только ${target} фишек`);
  }
  return null;
}
```

**Сравнение решений** (`better`) — лексикографическое по критерию варианта:

```ts
function score(s: Solution, variant: Variant): number[] {
  const nonZero = s.counts.filter(c => c > 0).length;
  const total = s.counts.reduce((a, b) => a + b, 0);
  switch (variant) {
    case 'balanced': return [nonZero, total];
    case 'economy':  return [total, nonZero];
    case 'speed':    return [-s.counts[0], total];
  }
}
```

**`maxReachable(d, cap)`** — максимальная сумма, которую физически можно собрать из набора
(без ограничений K и блайндов). Реализуется как задача о рюкзаке с ограниченным числом
предметов: `dp[s] = true`, если сумма `s` достижима; ответ — максимальный `s` с `dp[s]`.
Размер массива = `Σ cap[i]·d[i]` (для дефолтного набора ≤ 12 250), поэтому обычный
`Uint8Array` и цикл по номиналам работают за единицы миллисекунд. Нужен только для уровня L4.

### 4.6 Дефицит банка и покрытие докупок

Отдельно от лестницы считается **покрытие резерва**:

```
bankTotal      = Σ counts[i] · d[i]
dealt          = chipsPerPlayer × players
reserveNeeded  = reserveStacks × stackChips
stillInBank    = bankTotal − dealt
coveredStacks  = floor(stillInBank / stackChips)      // сколько полных докупок хватит
```

В UI на экране выбора раздачи и на экране игры:

> «Раздача: 600 фишек × 4 игрока = 2 400. В банке останется 9 850 — хватит на 16 докупок при резерве 4.»

Если `coveredStacks < reserveStacks`:

> «⚠ Резерв 4 докупки не покрывается: банк выдержит 16. Стек будет урезан до N фишек.»

Замечания к таблице:

- **L3** при 6+ игроках и стеке 2000: физически не хватает фишек, идёт симметричное урезание
  до максимальной достижимой суммы. Это ожидаемое поведение по §4.4, а не баг.
- **L1** в строке 8 игроков / K=10: кратность соблюдена и стек точный, но мелких фишек
  на блайнды не осталось (`a[0] = 0`) — гарантия блайндов снимается первой, до нарушения K.
  Дыры в этой строке законны: та же раздача на L0 не собирается.
- `exempt` — номинал, освобождённый от кратности K. В L3 его нет (K выключен).
- Строка 4 / 150 / 5 показывает, зачем нужен `exempt` у Economy: 600 = 5·100 + 3·25 + 5·5,
  где 3 не кратно 5; у Balanced теперь `[15,11,5,0]`, где не кратно 5 уже 11 фишек по 25.

**Какие провалы остаются у Balanced и почему** (это не баг, проверено тестом):

1. `[0,0,0,6]` (8–12 игроков, K=10, стек 600): на младший нет `a[0] ≥ 4` —
   `cap(5) = 6 < 4·K`; догнать нижнюю границу нечем, гарантия блайндов снята (L1).
2. `[10,10,0,5]` (6–7 игроков, K=10, стек 800): по 25 на игрока только 10 фишек,
   кратно 10 спишется 10, а 20 > cap; по 5 на блайнды нельзя (`4·K = 40 > cap 6`),
   освобождать промежуточный 25 вместо 5 — потерять размен.
3. `[5,3,0,5]` (12 игроков, K=5, стек 600): на 25 приходится 6 фишек, освобождённая
   пара — именно 25 (`a[1] = 3`), промежуточный 50 выдаётся только кратно K.

**Обязательные свойства, проверяемые тестами:**

1. `Σ a[i]·d[i] == chipsPerPlayer` для L0–L3.
2. `a[i] ≤ floor(counts[i]/players)` всегда.
3. `a[i] % K == 0` для всех `i ≠ exempt` на L0–L2.
4. `a[0] ≥ 4` на L0; на L0 также `a[1] == 0 || a[1] ≥ 2`.
5. `deal` одинаков для всех игроков.
6. Время расчёта < 300 мс для 12 игроков на любом входе (замерено: < 1 мс).
7. При одинаковом входе результат детерминирован.
8. `exempt` — не более одного индекса на решение.
9. Balanced: провал верха (§4.3) допустим только в случаях 1–3 выше.

**Замечание про K=4.** При K=4 и цели, не кратной 4, точное решение почти всегда
уходит на L1 (снимается гарантия блайндов) или L3. Пример: `n=4`, 150 монет, K=4
→ `[0,0,0,6]` = 600 на уровне L1. Это нормально: K=4 означает «четыре фишки на пачку»,
и на стеке 600 выгоднее отдать 6×100, чем соблюсти мелкие. В UI показывать уровень явно.

### 5.7 История `/history`

Список, новые сверху, группировка по месяцам («Октябрь 2026»).

Строка: `29 окт, 20:45 · 4 игрока · 🪙 +120` + бейдж статуса (`архив` / `завершена`).

Долгий тап или кнопка «…» → шит с действиями (Q137):
- «Открыть» → `/game/:id/results`
- «Поделиться» (только завершённые)
- «Новая игра с этими настройками» → `/new?clone=:id` (Q138)
- «Удалить» → двойное подтверждение (Q93)

### 5.8 Публичные итоги `/share/:payload`

Read-only карточка (Q131): тот же визуальный блок «топ + таблица», плюс дата, стек, курс,
блайнды. Без кнопок редактирования. Внизу кнопки «Скопировать ссылку» и «Поделиться»
(если `navigator.share` есть). При ошибке декодирования — вежливый экран (Q128).

### 5.9 Набор и дефолты `/settings`

Две секции на одной странице (Q110):

**Набор:** список строк `номинал · цвет · количество`, добавить/удалить (2..8 строк),
итог «12 250 фишек». Цвет — палитра из 8 пресетов + `<input type=color>` (Q74).

Поля «номинал» и «количество» — числовые, выравнивание по правому краю, и **не уже
четырёх разрядов** (`--num-field-min: 8.6ch`): столько занимают четыре монозначных
цифры плюс отступы и спиннеры `type=number`. `ch` берётся от текущего шрифта,
поэтому поле остаётся читаемым и при увеличенном масштабе текста. Набор — до
8 номиналов.

Строка набора двухстрочная: сверху поля «номинал × количество», растянутые на всю
ширину, снизу палитра (4 пресета) и кнопка удаления. В одну строку при 430 px
номиналу остаётся ~54 px, и палитра наезжает на поле количества.

**Дефолты:** стек, курс, малый блайнд, K, резерв. Кнопка «Сбросить к стандартным».

## 6. Поведение игры

### 6.1 Создание

По кнопке «Начать игру»:
1. Валидация (минимум 2 игрока, набор ≥ 2 номиналов, все поля > 0).
2. Создаётся `Game` со статусом `active`, копией набора и выбранным `Deal`.
3. Генерируются `deal`-события по одному на игрока.
4. Переход на `/game/:id`.

### 6.2 Докупка

`[＋]` у игрока → событие `buyin` на `stackChips`. Банк уменьшается.
Разрешено даже при отрицательном банке — показывается предупреждение (Q112).

### 6.3 Внешняя покупка

Шторка игрока → «Ещё» → «Внешняя докупка». Выбираются покупатель и продавец.
Создаётся событие `external`: у продавца `externalOut++`, у покупателя `externalIn++`.
Банк не меняется. В учёте: `boughtChips` растёт у обоих, но `externalOutChips`
компенсирует продавца — сумма итогов остаётся нулевой (Q91).

### 6.4 Ввод остатка (вывод игрока)

Шторка → «Вышел из игры» → поле «сколько осталось фишек» → событие `cashout`.
Игрок помечается `out`, фишки возвращаются в банк. Кнопки «вернуть в игру» **нет**;
ошибочный выход исправляется только через редактор журнала (Q125/Q134).

### 6.5 Финальные остатки

На экране итогов — блок «Финальные остатки». Для каждого игрока поле ввода →
событие `finalStack` (перезаписывает предыдущий `finalStack` этого игрока, а не добавляет новый).

### 6.6 Редактор журнала

Пока игра не архивная (Q78):
- список событий с временем и типом;
- правка суммы любого события;
- удаление любого события;
- добавление забытого события;
- «Отменить последнее действие» — снимает последнее событие.

Всё пересчитывается мгновенно (журнал — источник правды).

### 6.7 Заморозка настроек

После создания игры настройки (набор, стек, курс, SB, K, резерв, состав игроков)
**не редактируются** (Q121). Пересдача (`deal`) доступна только пока в журнале есть
только `deal`-события (Q122). Добавление игрока в процессе — отдельное действие (§6.8).

### 6.8 Добавление игрока в процессе

Создаётся игрок + `deal`-событие на `stackChips` (как обычная раздача). Требует наличия
фишек в банке; при нехватке — предупреждение, но не блокировка (Q48/Q112).

### 6.9 Завершение

«Итоги» → «В архив» → если не у всех есть `finalStack`:
«У 2 из 4 игроков остаток не зафиксирован. Всё равно завершить?» (Q77/Q135).
Затем — мини-игра (§7), затем `status = 'archived'`, `archivedAt = now`, read-only.

До архивации можно «Завершить» (status `finished`) — игра закрыта, но остатки ещё можно
дописывать. Это два разных шага (Q136).

## 7. Мини-игра подтверждения архивации

Реализация — отдельный компонент `components/ArchiveGate.tsx` (Q50/Q123).

- Показывается последовательность **1 → 2 → 3 → 4** (крупно, сверху).
- Ниже — область высотой ~50vh, в которой четыре круга с цифрами 1–4 расставлены
  в **случайных непересекающихся позициях** (алгоритм: 4 случайных точки, минимум 88 px
  между центрами, отступ 16 px от краёв).
- Пользователь тапает в порядке 1, 2, 3, 4.
- Ошибка → сброс прогресса (позиции **не** пересчитываются), вибро-отклик об ошибке.
- Успех → `navigator.vibrate(20)`, архивация.
- Внизу — «Отмена».
- `prefers-reduced-motion` — без анимаций появления.

## 8. Хранилище

### 8.1 Схема IndexedDB

База `pokernight`, версия `1`.

| Store | Key | Значение | Индексы |
|---|---|---|---|
| `games` | `id` | `Game` | `by-status`, `by-createdAt` |
| `settings` | `id` (`'kit'` / `'defaults'`) | `Kit` \| `Defaults` | — |

```ts
// db/schema.ts
export interface DBSchema extends DBSchema {
  games: {
    key: string;
    value: Game;
    indexes: { 'by-status': GameStatus; 'by-createdAt': string };
  };
  settings: {
    key: 'kit' | 'defaults';
    value: Kit | Defaults;
  };
}
```

### 8.2 Первый запуск

Если оба ключа `settings` пусты, записываются:

```ts
const DEFAULT_KIT: Kit = {
  id: 'kit',
  denominations: [
    { id: 'd1', value: 5,   color: '#c8443b', count: 75 },  // красные
    { id: 'd2', value: 25,  color: '#2f9e6a', count: 75 },  // зелёные
    { id: 'd3', value: 50,  color: '#2f6fd0', count: 50 },  // синие
    { id: 'd4', value: 100, color: '#2b2b2b', count: 75 },  // чёрные
  ],
  updatedAt: new Date().toISOString(),
};
// всего 12 250 фишек

const DEFAULT_SETTINGS: Defaults = {
  id: 'defaults',
  stackCoins: 150,
  rate: 4,
  smallBlindChips: 5,   // = мин. номинал
  multipleK: 5,
  reserveStacks: 4,     // = дефолтное число игроков (Q53)
  updatedAt: new Date().toISOString(),
};
```

Дефолты применяются **один раз при первом запуске** (Q120). Дальше новая игра
читает `Defaults` при открытии `/new`, но пользователь может их менять на `/settings`.
Активная игра свои замороженные настройки уже не перечитывает (§6.7).

### 8.3 Активная игра

В любой момент времени максимум одна игра со `status = 'active'` (Q30).
При создании новой игры, если есть активная:

> «У вас есть незавершённая игра. [Завершить её] [Оставить в истории и начать новую] [Отмена]»

Второй вариант переводит текущую в `finished` без мини-игры (Q82/Q86).

### 8.4 Квоты и ошибки

Запись обёрнута в try/catch. При `QuotaExceededError` — тост «Не удалось сохранить: нет места».
При недоступном IndexedDB (приватный режим) — работа в памяти + плашка «Данные не сохраняются»
(Q132).

## 9. Публичная ссылка

### 9.1 Формат

`/<base>/share/<payload>`, где `payload = base64url(codecByte ‖ compressedJSON)`.

- `codecByte`: `0x01` = `deflate-raw`, `0x02` = `brotli` (Q75).
- **Кодируем всегда `deflate-raw`** (доступен везде с 2023).
- **Декодируем оба**: при `0x01` — `deflate-raw`, при `0x02` — `brotli`, если
  `CompressionStream('brotli')` доступен; иначе — экран «ссылка создана в браузере,
  который не поддерживается этим устройством».
- `base64url`: стандартный алфавит с заменой `+`→`-`, `/`→`_`, без `=`.

### 9.2 Данные (компактные ключи)

```json
{
  "v": 1,
  "t": "2026-10-29T20:45:00+10:00",
  "s": 150,
  "r": 4,
  "sb": 5,
  "k": 5,
  "p": [
    { "n": "Антон", "f": 1240, "b": 1, "e": 0, "x": 0 }
  ]
}
```

| Ключ | Значение |
|---|---|
| `v` | версия схемы (1) |
| `t` | дата игры, ISO 8601 с offset |
| `s` | стек в монетах |
| `r` | курс (фишек за монету) |
| `sb` | малый блайнд в фишках |
| `k` | кратность K |
| `p[].n` | имя (≤ 24 символов) |
| `p[].f` | финальные фишки |
| `p[].b` | докупок из банка |
| `p[].e` | внешних получено |
| `p[].x` | внешних отдано |
| `p[].h` | необязательное: фишки на руках на момент ссылки. Нужно только при `f: null`, чтобы публичная страница считала `net` по тем же формулам §3.4, что и экран итогов (иначе «остаток не зафиксирован» давал бы `net = −bought`) |

Журнал событий в ссылку **не попадает** (Q115). Если у игрока нет `finalStack` — `f: null`,
`h` — фишки на руках, и на публичной странице пометка «остаток не зафиксирован».
Поле `h` опционально: старые ссылки его не содержат и читаются как раньше (§9.3).

### 9.3 Обещание совместимости

Старые ссылки должны открываться всегда (Q67). Правило: новые поля добавляются только
опциональными; при `v > 1` приложение читает известные поля и игнорирует неизвестные,
показывая плашку «ссылка новее приложения» только если критичных полей нет.

### 9.4 Размеры (замерено)

JSON с 12 игроками — ~600 B, `deflate-raw` — 248 B, Base64URL — **331 символ**.
С длинными именами — 920 B → 276 B → 368 символов.
Цель ≤ 800 символов для 12 игроков (Q116) выполняется с большим запасом.
Имена обрезаются до 24 символов.

## 10. Service Worker и офлайн

### 10.1 Стратегии (Q68/Q111)

Собственный SW (~80 строк), без Workbox. Precache-список генерируется build-хуком
из `vite`-манифеста.

| Запрос | Стратегия |
|---|---|
| Навигация (`mode: 'navigate'`) | network-first → фоллбек на `index.html` из кэша |
| `/assets/*` (хэшированные) | cache-first, immutable |
| manifest, иконки | stale-while-revalidate |
| прочее (внешние) | не кэшируем |

Версия кэша = хэш сборки; при активации старые кэши удаляются.

### 10.2 Обновления (Q60)

- `registration.onupdatefound` → новый SW в состоянии `installed` → показываем тост
  «Доступно обновление» с кнопкой «Перезагрузить».
- Кнопка отправляет `postMessage({type:'SKIP_WAITING'})`, SW вызывает `skipWaiting()`,
  страница слушает `controllerchange` и делает `location.reload()`.
- Без тоста SW активируется при следующем визите.

## 11. Визуальный язык

### 11.1 Палитра (Q98/Q103)

```css
:root {
  --bg:            #0d1512;
  --bg-elevated:   #16211d;
  --bg-glass:      rgba(22, 33, 29, 0.72);
  --felt:          radial-gradient(ellipse at 50% 0%, #17352a 0%, #0d1512 62%);
  --gold:          #d4af37;
  --gold-soft:     #e8c95a;
  --gold-gradient: linear-gradient(135deg, #d4af37 0%, #f4e08a 50%, #b8932a 100%);
  --green:         #2f9e6a;
  --red:           #c8443b;
  --text:          #f2f0eb;
  --text-dim:      #9aa39e;
  --border:        rgba(212, 175, 55, 0.22);
  --shadow:        0 8px 32px rgba(0, 0, 0, 0.45);
}
```

- Только тёмная тема, `color-scheme: dark`.
- Стеклянные панели: `background: var(--bg-glass); backdrop-filter: blur(8px);`
  + `@supports not (backdrop-filter: blur(1px))` → сплошной фон.
- Золотой градиент — на главной кнопке, акценте «топ», заголовке экрана.

### 11.2 Моушн (Q99/Q101)

Без библиотек. Три техники:

1. **View Transitions API** для смены маршрута:
   `document.startViewTransition(() => render())`, с фоллбеком на мгновенную замену.
   Длительность 180 мс, `ease-out`.
2. **CSS-анимации появления** карточек: `@keyframes rise` (transparent→opaque, translateY 8px→0),
   stagger через `style="--i: n"` и `animation-delay: calc(var(--i) * 30ms)`.
3. **FLIP-перелёт фишки** при докупке: замер `getBoundingClientRect` источника и цели,
   `element.animate([...], {duration: 320, easing: 'cubic-bezier(.2,.8,.2,1)'})`.

Плюс **roll-up цифр** на экране итогов: тикер на `requestAnimationFrame`, 400 мс,
`easeOutCubic`, ~30 строк.

`prefers-reduced-motion: reduce` → все анимации отключаются (длительность 0).

### 11.3 Тактильность

`navigator.vibrate(10)` на: докупка, вывод, финальный остаток, успешная архивация.
На ошибку в мини-игре — `navigator.vibrate([20, 40, 20])`. Без звука (Q108).

### 11.4 Язык текстов

Без глаголов и обращений (Q89): «Игроки», «Стек», «Старт», «Банк», «Итоги».
Сообщения об ошибках — короткие существительные: «Дубликат имени», «Нет места».

## 13. Критерии приёмки

Функциональные:

- [ ] Первый запуск создаёт дефолтный набор и дефолты.
- [ ] Игра создаётся, три варианта раздачи видны, все три дают ровно стек (кроме L3/L4).
- [ ] Раздача хватает на всех: `a[i]·n ≤ counts[i]`.
- [ ] Докупка, внешняя покупка, вывод, финальный остаток меняют итоги ожидаемо.
- [ ] `Σ netChips == 0` после ввода всех остатков.
- [ ] Редактор журнала пересчитывает всё.
- [ ] Архивация требует мини-игру, после неё игра read-only.
- [ ] Ссылка открывается в новой вкладке и показывает те же итоги.
- [ ] История, клон, удаление работают.
- [ ] Офлайн после первой загрузки: приложение открывается и работает.
- [ ] Все 11 строк golden fixtures из §4.7 воспроизводятся точно (включая случай 4 / 150 / 5:
      Balanced даёт `[15,11,5,0]`, без дыры 50).
- [ ] Balanced не оставляет провалов верха (§4.3) ни на одном входе, кроме перечисленных
      в §4.7 случаев, где догнать нижний край нечем.

Нефункциональные:

- [ ] Расчёт раздачи < 300 мс для 12 игроков (замерено < 1 мс).
- [ ] JS-бандл < 120 КБ gzip, CSS < 25 КБ gzip.
- [ ] Нет горизонтального скролла на 320–430 px.
- [ ] Все тапы ≥ 44 px.
- [ ] 6 игроков помещаются на 375×689 без скролла.
- [ ] `pnpm typecheck`, `pnpm test`, `pnpm lint`, `pnpm build` зелёные.
- [ ] `prefers-reduced-motion` отключает анимации.

## Приложение A. Тексты уровней раздачи для UI

| `deal.level` | Плашка | Пояснение |
|---|---|---|
| `L0` | — (нет плашки) | Всё идеально |
| `L1` | «без мелких на блайнды» | Стек и кратность соблюдены, но фишек младшего номинала нет |
| `L2` | «−N фишек на игрока» | Стек отличается на N (1–2) |
| `L3` | «кратность ослаблена» | K не соблюдён, стек точный |
| `L4` | «банк не позволяет полный стек» | Урезано до максимально возможного |

## Приложение B. Журнал решений

Краткая сводка принятых решений — чтобы реализатор понимал «почему так», не перечитывая
всю спеку. Номера `Q` — из интервью.

**Экономика.** Монеты = фишки / rate; rate — целое «фишек за монету», задаётся в игре (Q6–Q9).
Стек вводится в монетах, блайнд в фишках, BB = 2×SB только отображается (Q43–Q45, Q70, Q117).
Монеты хранятся в сотых, фишки — целые (Q95).

**Учёт.** Только суммы, не номиналы (Q20). Докупка = +1 стандартный стек из банка (Q11, Q22).
Вывод = остаток в банк, возврата нет (Q13, Q125, Q134). Внешняя покупка = перевод стека
от продавца покупателю за деньги, банк не участвует, сумма итогов нулевая (Q48, Q52, Q80,
Q91, Q126). Сверка показывается, но не блокирует архивацию (Q14). Нет кассы (Q59).

**Раздача.** Три варианта с разными целевыми функциями (Q2, Q18, Q19, Q57, Q113):
Balanced = без провалов на верхней границе стека (мелкий 25/50 не пустует при живых
крупных), затем ровный верх по фишкам и уже потом min разных номиналов;
Economy = min фишек, Speed = max мелких.
Все дают одинаковый набор всем игрокам (Q54). Кратность K жёсткая, кроме одного
освобождённого номинала (Q3, Q141). Дефицит банка → симметричное урезание + покрытие
(Q4, Q142). ±1–2 фишки допустимы с явным показом (Q143). Учитывается наличие по номиналам
на старте (Q76, Q94).

**Модель.** Плоская: игра = сессия = вечер (Q10). Одна активная игра (Q30).
Глобальный «Мой набор» + дефолты, копия в игру при создании (Q15, Q84, Q96, Q110).
Изменения обратимы до архивации через журнал событий (Q49, Q78, Q121, Q122).
Финальные остатки → архив (Q47, Q90, Q135, Q136).

**Веб.** pnpm + TS + Preact + Vite + kinu + lucide-preact + idb + vitest + Biome (Q35, Q36,
Q102, Q106, Q144). History-роутинг + 404.html (Q27, Q28). Свой SW + build-хук, без Workbox
(Q68, Q107, Q111). PWA-манифест (Q61). Тост обновления (Q60).

**Ссылка.** Brotli пишем только если есть, читаем оба; кодируем deflate-raw с тегом кодека
(Q25, Q75). Данные — только итоговая таблица (Q24, Q115). Версия в payload (Q67).
Цель ≤ 800 символов (Q116), фактически 331–368.

**UI.** Тёмная тема, золото/зелень/красный, стекло + градиенты (Q38, Q98, Q99, Q103).
Только мобильная ширина, 430 px, 6 игроков на 375×689 (Q109, Q114). Тексты без глаголов
(Q89). Вибро без звука (Q108). Моушн без библиотек: View Transitions + CSS + WAAPI (Q101).
Мини-игра архивации: цифры 1–4 в случайных позициях (Q50, Q123).

**Границы.** Только русский (Q5). Лицензия MIT (Q148). Без экспорта базы (Q56).
Одна вкладка (Q146). Браузеры 2023+ (Q37). Без жёсткого бюджета бандла (Q73).
